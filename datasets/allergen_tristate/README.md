# 菜品—过敏原三态数据集

面向「和议」私密协商器的可提交、可复现数据集，用于三态属性层、提问预算实验与初赛材料「数据集选取与处理」一栏。

- 规模：**184 道菜**、**153 种配料**、**14 类过敏原**、**8 个用餐场景**、**10 个来源**
- 过敏原三态：`CONTAINS`（已知含）、`NOT_CONTAINS`（已知不含）、`UNKNOWN`（未知）
- 固定随机种子：`20261110`
- 构建脚本：`scripts/build_dataset.py`，仅使用 Python 标准库
- 输出目录：`output/`；本目录独立，未修改 `backend/app` 下任何实现代码

## 1. 快速开始

在本目录下执行：

```powershell
python scripts\build_dataset.py
python scripts\build_dataset.py --check
```

第一条命令重新生成 `output/` 下全部文件；第二条命令用同一固定种子重建并与磁盘结果逐字节比对。输出不含时间戳，重复运行结果一致。

## 3. 字段说明

### 3.1 菜品输出 `output/dishes_allergen_tristate.csv`

| 字段 | 含义 |
| --- | --- |
| `dish_id` | 菜品稳定编号，如 `D001` |
| `name` | 菜品名 |
| `cuisine` | 菜系或品类，如川菜、粤菜、日料、火锅、早餐 |
| `scenarios` | 适用用餐场景，多个用 `;` 分隔 |
| `price_cents` | 参考单价，单位分；仅用于演示预算约束 |
| `price_source` | 价格来源，当前全部为 `P1`（市场参考价，非权威） |
| `gluten` … `lupin` | 14 类过敏原三态列，取值为 `CONTAINS` / `NOT_CONTAINS` / `UNKNOWN` |
| `contains_allergens` | 该菜所有 `CONTAINS` 的过敏原代码 |
| `unknown_allergens` | 该菜所有 `UNKNOWN` 的过敏原代码 |
| `not_contains_allergens` | 该菜所有 `NOT_CONTAINS` 的过敏原代码 |
| `source_ids` | 菜品配方来源编号，对应 `data/sources.csv` |
| `credibility` | 过敏原证据可信度，取配料链中最低一级：A > B > C > D |
| `manual_review` | `1` 表示存在人工复核/修正或至少一个 `UNKNOWN`；`0` 表示纯规则推定且无未知 |
| `note` | 配方变体、复合调料或交叉接触说明 |

### 3.2 长表 `output/dishes_allergen_long.csv`

每行一个「菜品 × 过敏原」，共 `184 × 14 = 2576` 行。新增 `basis_ingredient_ids` 字段：`CONTAINS` 记录触发该状态的配料，`UNKNOWN` 记录导致未知的配料，`NOT_CONTAINS` 为空。

### 3.3 JSONL `output/dishes_allergen_tristate.jsonl`

每行一个菜品，`allergens` 为嵌套对象，每个过敏原包含 `state` 与 `basis`，适合直接入库或做实验分析。

### 3.4 配料输入 `data/ingredients.csv`

`state_overrides` 只写非 `NOT_CONTAINS` 的状态，例如：

```text
gluten=contains;soy=contains;sulphite=unknown
```

未列出的过敏原按 `NOT_CONTAINS` 处理。这一默认值不是猜测：该配料必须在 `evidence` 中给出单一食材或权威成分表依据；复合调料、加工食品和配方不固定项必须显式写入 `unknown`。

## 4. 标注与聚合规则

完整规则见 [docs/annotation-spec.md](docs/annotation-spec.md)。核心只有四条：

1. **CONTAINS**：配料本身即致敏原，或权威标准/配料表明确列出该致敏原。
2. **NOT_CONTAINS**：权威成分表能确证该配料不含该致敏原，且不存在配方变体或交叉接触。
3. **UNKNOWN**：复合调料、加工食品、配方不固定、来源未覆盖、交叉接触不可排除，一律记未知。
4. **禁止推断**：不得因菜名不含某物、或「通常不放」就判 `NOT_CONTAINS`；无法确证必须记 `UNKNOWN`。

菜品状态由配料状态聚合：

```text
任一配料 CONTAINS        -> 菜品 CONTAINS
否则任一配料 UNKNOWN     -> 菜品 UNKNOWN
否则                     -> 菜品 NOT_CONTAINS
```

即 `CONTAINS > UNKNOWN > NOT_CONTAINS`。配料冲突时取更保守的状态；未知不会被静默降级为「不含」。

补充说明：

- S1–S3 与 S7 只用于确定**过敏原分类**，不直接证明某道菜含或不含某物；具体菜品结论由 S4–S9 的配料证据推导。

- 价格 `P1` 是 2026-11 华东地区餐馆/外卖常见价位的整理值，**不是抓取数据，也不是过敏原证据**；生产使用时应替换为用户导入的真实菜单价格。

## 7. 与后端三态属性层的对接

建议把 14 列映射为后端的 `attributes`。后端三态枚举是 `present` / `absent` / `unknown`，属性 key 为 1–64 字符的自由字符串（测试与 OCR 链路使用 `peanut`、`花生` 这类 key）：

```json
{
  "candidate_id": "D001",
  "name": "麻婆豆腐",
  "cost_cents": 2800,
  "category": "川菜",
  "attributes": [
    {"key": "gluten", "state": "present", "source": "import"},
    {"key": "soy", "state": "present", "source": "import"},
    {"key": "sulphite", "state": "unknown", "source": "import"},
    {"key": "egg", "state": "absent", "source": "import"}
  ]
}
```

映射关系：

```text
CONTAINS     -> present   硬约束命中，直接排除
NOT_CONTAINS -> absent    可视为满足
UNKNOWN      -> unknown   不得静默当作安全，应触发追问或人工确认
```

这正好对应 AI 主线：AI 只负责把 `unknown` 变少（结构化菜单、解析自然语言约束、生成追问），不参与打分、不修改硬约束、不代替成员确认。场景文件可直接作为单次 13–30 项候选的输入。

## 8. 已知局限

1. **配方是通用做法**：同一道菜在不同地区、餐馆、家庭的做法不同，数据集只覆盖常见配方，不覆盖所有变体。
2. **复合调料导致大量 UNKNOWN**：酱油、蚝油、豆瓣酱、火锅底料、咖喱块、腌腊制品等配方差异大，按规范一律记未知；这是数据设计的一部分，不是缺陷。
3. **交叉接触只建模了共用炸油**：案板、烤架、油锅过滤、服务分餐等环节未建模；真实过敏风险管理仍需餐厅确认。
4. **精炼花生油/芝麻油的争议**：精炼油蛋白残留很低，但标签口径与医学建议并不完全一致；本数据集按标签保守记为 `CONTAINS`。
5. **非欧盟 14 类食材**：椰子、板栗、莲子、海参不在欧盟 14 类清单内，按 `NOT_CONTAINS` 处理并在配料备注中说明；对个别患者的临床意义需另行判断。
6. **羽扇豆无正例**：中文聚餐菜单几乎不使用羽扇豆，`lupin` 全部为 `NOT_CONTAINS`，不能用于羽扇豆阳性实验；需要时应补充西式无麸质烘焙样本。
7. **芹菜正例很少**：中式菜谱中芹菜使用频率低，`celery` 仅 1 个 `CONTAINS` 正例，相关实验结论的统计效力有限。
8. **价格不可追溯**：`price_cents` 是演示用参考价，不是抓取的市场数据，不能用于经济分析；生产应替换为用户导入的真实菜单价格。
9. **不是实验室检测**：所有状态来自标准、成分表、配料表与菜谱的文献证据，不是逐菜品检测结果，不能替代医生或餐厅的过敏原确认。
10. **酒类澄清剂未建模**：葡萄酒/啤酒可能使用蛋清、鱼胶、明胶等澄清剂，本数据集只建模了亚硫酸盐与啤酒麸质。
11. **份量与烹饪方式未建模**：同一菜品在不同份量、不同烹饪时间下的过敏原风险未细分。
12. **`manual_review` 是数据质量标记**：`1` 表示需要人工复核或已人工修正，不等同于临床验证或官方认证。

## 9. 初赛材料可直接引用的说明

> 本数据集面向小团队聚餐场景，覆盖 184 道常见菜品、153 种配料与 14 类过敏原（中国 GB 7718 的 8 类 + 欧盟 1169/2011 的 6 类扩展），按川、粤、鲁、苏、浙、湘、徽、东北、西北、云贵、家常、火锅、烧烤、日料、西餐、素食、早餐等菜系和 8 个用餐场景组织，可直接生成 13–30 项的单次协商候选集。数据采用「配料级证据 + 三值逻辑聚合」构建：每个配料按权威标准、食物成分表、包装配料表与菜谱证据标注「含 / 不含 / 未知」，菜品状态由配料状态聚合，任一配料含即含，否则任一配料未知即未知，全部确证不含才判不含；无法确证的复合调料、加工食品与交叉接触一律记未知，禁止用推测填补「不含」。数据集附来源登记表、许可说明、标注规范、固定种子构建脚本与 SHA256 清单，`python scripts/build_dataset.py --check` 可逐字节复现。当前统计：184 道菜中 138 道存在未知项或需人工复核，未知项均值 1.408 个/菜，亚硫酸盐未知率 42.9%、麸质 13.6%、大豆 12.5%，说明「未知」是真实存在的常态，而不是可以忽略的噪声；这也为 AI 主线提供了明确的优化目标——通过结构化菜单、自然语言约束解析与追问生成降低未知率，从而减少硬约束对提问预算的占用。

## 10. 复现与校验

- 随机种子：`20261110`；可用 `--seed` 覆盖，但正式提交请使用默认种子。
- 场景抽样：在每个场景候选池内按「新增（过敏原, 状态）覆盖 > 新菜系 > 新价格带」贪心选取，平局按固定洗牌顺序决定。
- 输出不含时间戳；`manifest.json` 记录全部输入与输出的 SHA256。
- `--check` 不写盘，只在内存中重建并逐字节比较；任何不一致以非零退出码结束。
- 新增或修改 `data/*.csv` 后，先运行构建，再运行 `--check`，两者都通过才算数据可用。

## 11. 维护约定

- 新增配料必须写明 `evidence`、`source_ids`、`credibility`；非 `NOT_CONTAINS` 状态必须在 `state_overrides` 中显式列出。
- 新增菜品必须列出全部致敏性配料；盐、糖、水、普通食用油可不单列，但花生油、芝麻油、黄油、蚝油、酱油等必须列出。
- 新增场景必须保持候选池 ≥ 13 项、目标候选数在 13–30 之间。
- 修改过敏原分类或聚合规则属于契约变更，需同步更新 `docs/annotation-spec.md`、`README.md` 与版本号。
